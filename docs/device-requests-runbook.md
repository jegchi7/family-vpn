# Заявки на устройства · v0.6.0

После `npm run setup`, `npm run build`, `npm run auth` войдите обычным пользователем. Нажмите «Добавить устройство», задайте название и ОС, затем «Сохранить заявку». Устройство появится в списке со статусом **«Ожидает настройки»**, с двумя ожидающими профилями AWG и REALITY. Данные сохраняются при перезагрузке страницы и перезапуске приложения.

Это заявка в локальной базе, а не подключение VPN: адрес, ключи, peers и рабочие конфиги пока не выдаются. Ни один запрос не вызывает агент или shell. Подбор проверенного приложения и импорт конфигов — следующие DEV-07/08/09.

## Изменение заявки

- «Переименовать» сохраняет название; UI передаёт текущую revision. Если запись изменена в другом окне, сервер возвращает конфликт без перезаписи чужих изменений. Нажмите «Обновить список» и откройте переименование заново.
- «Отменить заявку» доступно для pending-записи, созданной новым request flow, до появления настроенных профилей/секретов/адреса/installed revision/подписки. Требуется подтверждение в интерфейсе. Отмена переводит запись и profile slots в revoked, освобождает активный слот и оставляет историю.
- Отмена **не является отзывом работающего VPN**. Если профиль уже выдан, есть другое поколение или legacy device без request marker, API отклоняет действие. Сетевой revoke и проверка его завершения относятся к DEV-19.

Квота по умолчанию — 5 неотозванных устройств на пользователя; pending тоже занимает слот. Временный предел всей истории — 200 записей на пользователя до реализации retention. При исчерпании истории API возвращает DEVICE_LIMIT; UI показывает только активную квоту. Admin UI управления лимитом пока нет. Значение device_limit хранится в user record; менять его вручную в live DB этим runbook не предлагается.

## Повторы и данные

`POST /api/v1/devices` принимает request_id/name/os. Request ID находится в памяти формы до подтверждённого успеха. Повтор с тем же ID и нормализованными параметрами возвращает текущее устройство, не создаёт копию и не занимает новый слот. Другое содержимое с тем же ID → 409. После отмены старый ID по-прежнему возвращает закрытую запись, не восстанавливает доступ. Перезагрузка формы создаёт новый пользовательский запрос: перед повторным добавлением после сетевой ошибки проверьте список.

Переименование и отмена требуют expected_revision. Owner берётся только из сессии, передача owner_id/user_id в JSON запрещена. Чужое и отсутствующее устройство отвечают одинаковым 404. Demo остаётся read-only; на admin listener эти endpoints не зарегистрированы. Admin overview считает все записи, включая закрытые; пользовательская квота считает только неотозванные.

Идентификаторы/названия устройств не являются VPN-ключами. Audit содержит actor/action/device ID, без payload/пароля/конфигов. Ошибка audit откатывает транзакцию. Обработчик проверяет сессию до мутации; уже начавшийся запрос не отменяется задним числом при одновременном logout/recovery. Это ограничение локального lifecycle, не обещание строгого глобального отсечения всех in-flight запросов.

## Обновление v0.5 → v0.6

Остановить локальные HTTP-процессы, сохранить исходную БД по принятой локальной процедуре, распаковать новую версию кода и перенести только нужный private state. `npm run setup && npm run build`, затем:

```sh
./build/vpnctl auth-init --root var/auth
```

CLI применяет portal migration v3→v4: request metadata/indexes; старые devices/profiles/accounts/sessions сохраняются. Runtime со старой схемой откажется стартовать, сам миграции не делает. `npm run auth` также вызывает auth-init. Demo обновляется через demo-init; admin DB остаётся v1, control v2. Не распаковывать source snapshot поверх каталогов с незакоммиченными изменениями или ключами.

## Проверки

`npm run check`, `npm run build`, `npm run test:persistence`; `npm run test:e2e:auth` включает user auth и devices.spec.ts. Отдельно `npm run test:e2e` и `npm run test:e2e:admin` проверяют общую оболочку.

Go tests покрывают owner boundary, idempotency/payload conflict, last-slot race через два DB handles, stale revision, cancel guard, audit rollback и миграцию v3→v4. Browser flow проверяет request/reload/conflict/rename/cancel/quota на desktop и 320 px. Работа на настоящих мобильных VPN-клиентах этим не проверяется.
