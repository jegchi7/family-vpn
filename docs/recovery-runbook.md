# Восстановление доступа · локальный стенд v0.5.0

## Обновление с v0.3.0

Остановить локальные процессы. Перенести существующий `var/auth` в новый checkout при необходимости; не помещать его в Git. Выполнить:

```sh
npm run setup
npm run build
npm run auth
```

Runner вызывает `auth-init`: portal schema обновится до v3, текущие аккаунты/сессии/приглашения сохранятся. Ручной HTTP startup со старой схемой завершается ошибкой. Control DB не затрагивается. Это не backup/restore процедура: нельзя считать копирование одного live WAL .db корректной резервной копией.

## Забытый пароль активного пользователя

После проверки личности пользователя выполнить на доверенном компьютере:

```sh
./build/vpnctl auth-recovery --login family-test
```

Windows: `./build/vpnctl.exe`. Нестандартный каталог: `--root <state-root>`. Короткий срок, например: `--recovery-ttl 10m`. По умолчанию 15 минут, максимум час.

**Эта команда сразу отключает старый пароль и отзывает все сессии кабинета этого пользователя.** VPN-профили и устройства сохраняются. Token из JSON передать вручную по выбранному доверенному каналу; CLI никому ничего не отправляет. Не помещать вывод в общий лог, Git, URL или скриншот.

Пользователь открывает https://127.0.0.1:8443, выбирает «Забыли пароль?», вставляет код, вводит и повторяет новый пароль. После подтверждения видит «Пароль обновлён» и входит обычным способом. Автоматического входа нет. Код используется один раз.

При потере или истечении кода повторить CLI-команду: предыдущий код будет отозван. Старый пароль не восстанавливается. Пока нового успешного reset нет, кабинет закрыт. Если команда вернула ошибку до commit, изменения откатываются; если stdout не удалось получить после успешного commit, просто выдать новый код.

Admin, disabled и ещё не активированные аккаунты этим способом не восстанавливаются. Путь пока только password-only user; passkey/TOTP credentials блокируют его, чтобы не обходить MFA. Admin MFA использует отдельную DB и собственный console reset (см. admin-auth-runbook.md).

## Истёкшее или потерянное приглашение

Для пользователя, который ещё ни разу не активировал кабинет:

```sh
./build/vpnctl auth-reissue-invite --login family-test
```

Новый код использовать в «У меня приглашение». Login/user id сохраняются, прежнее приглашение отзывается. TTL по умолчанию 24 часа, `--invite-ttl 1h` задаёт другой срок ≤24 часов. Для active аккаунта команда откажет: нужен recovery.

## Ошибки

- «Не удалось восстановить доступ»: проверить поле кода и пароль (≥12 символов, ≤1024 UTF-8 bytes); код мог истечь, быть использован или заменён. Запросить новый у администратора.
- «Слишком много попыток»: подождать до 5 минут; restart не обнуляет лимит. Общий IP учитывается совместно с остальными auth действиями.
- CSRF: «Обновить форму» заново получает preauth cookie/token. Cookies обязательны; токены не сохраняются в localStorage.
- Если соединение оборвалось после отправки нового пароля, сначала попробовать обычный login с новым паролем: commit мог уже завершиться. Повторный consume тогда корректно отклоняется.
- Нет восстановления через публичный API по одному login и нет автоматического обхода роли/state.

## Проверка после изменения

`npm run check`, `npm run build`, `npm run test:persistence`, `npm run test:e2e`, `npm run test:e2e:auth` (с установленным Playwright Chromium). Auth E2E проверяет также recovery на desktop/mobile. Скриншоты делать только с пустыми полями кода/пароля.

Это localhost development flow. Не публиковать его наружу и не использовать тестовый self-signed TLS как production конфигурацию.
